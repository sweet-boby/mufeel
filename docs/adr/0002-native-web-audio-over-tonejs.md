# 0002 用原生 Web Audio 而不是 Tone.js 播放稀疏采样

日期：2026-09-27
状态：已采纳

## 背景

音色方案最初定的是「Tone.js + Salamander 钢琴采样」。落地时发现两个事实：

1. Salamander 采样集本身是**稀疏**的：只有每 3 个半音一个采样（C、D#、F#、A），共 28 个文件，
   覆盖 C1–A7。中间的音必须靠取最近采样 + 变速变调补齐。这不是资源缺失，所有 Web 钢琴采样器都这么做。
2. 这个练习对播放的要求很具体：每个音的时长与音间留白必须可配（属于领域配置）、
   一串音播完要能 await、换题时要能立刻停止、并且**永远不能把界面卡在「正在播放」**。

Tone.js 的 `Sampler` 会把「哪个音用哪个采样、变调多少」交给内部处理，反而遮住了本项目最需要测的那部分逻辑；
它的调度语义也与我们需要的「逐音时序 + 播完即 resolve」不完全对齐。

## 决定

用原生 Web Audio 实现 `AudioPlayer` 端口：

- **采样映射是纯逻辑**，放在 core 的 `value-objects/sample-map.ts`（`assignSample`：选哪个采样、变调几个半音），
  由测试直接校验映射表与磁盘文件一一对应，并验证练习音域内变调不超过 1 个半音。
- **播放器只做执行**：fetch + decode 采样、按音高取 buffer、按 `playbackRate` 与配置时序调度、
  每个音结尾加短淡出避免咔哒声。
- **收尾双保险**：`onended` 触发即收尾；同时按「理论播放时长 + 余量」挂一个兜底定时器。
  后台标签页或音频上下文被挂起时 `onended` 可能不触发，没有兜底就会永久禁用一个本该可用的界面。

## 后果

- 少一个运行时依赖；播放路径完全可读、可调、可测。
- 代价是要自己管 AudioBufferSourceNode 的生命周期（停止、淡出、兜底收尾），
  这部分已经收敛在一个文件里（`apps/web/src/infrastructure/web-audio-piano-player.ts`）。
- 安卓端换播放器时，只需实现同一个 `AudioPlayer` 端口；采样映射与音色无关的那部分逻辑可以直接复用。

## 考虑过的替代方案

- **Tone.js `Sampler`**：代码更短，但把采样选择与变调藏进库里，项目最该测的一块变得不可测；
  且多一个依赖只为省几十行调度代码。
- **每个半音都放采样**：音高准确度最好，但仓库要多出十几 MB，而练习音域内本来就只有 1 个半音以内的变调。
