# 0004 音乐内容住进 core，显示名留在平台

日期：2026-09-27
状态：已采纳

## 背景

0003 把 earpath 的课程与七个模块搬进 `apps/web` 时，只把**排序题**接回了 `packages/core`，
其余六个模块（音程、和弦、音阶、音级、和弦进行、旋律）的乐理数据与出题规则留在了 web。
当时的说法是「课程是产品，不住 core」——这条对**课程形状**（几关、怎么解锁、练什么顺序）成立，
但**顺手把音乐事实也一起留下了**，这是一个没有被写进 0003 的代价：

- `INTERVALS`（16 条）、`CHORDS`（21 条）、`SCALES`（15 条）、`DEGREES`（12 条）、
  `NUMERALS`（10 条）、`CADENCES`（2 条）——76 条平台无关、语言无关的音乐事实；
- `voiceNumeral`（把级数摆成听得出性质的柱式和弦）与旋律的出题规则（允许哪些音级、级进的权重、
  变化音点缀）——两条纯算法，只依赖随机源。

这些内容与 `packages/core` 里已有的 `assignSample`（挑采样）、`positionsOf`（算名次）是同一类东西：
不碰平台、不碰文案、可以被任何前端复用。把它们留在 web，等于安卓端将来要一个字一个字重打一遍，
而 core 存在的理由恰恰是「平台无关的东西只写一次」。

同时，apps/web/src/domain/ 这个目录名也站不住了（本次一并拆掉）：里面装的其实是「内容 + 课程 + 出题协议」，
其中只有 `playback.ts`（一个纯数据类型）勉强算领域，其余是内容、产品配置与出题策略。
两个同名 `domain` 目录摆在一起，看代码的人第一反应必然是「这俩是不是重复了」。

## 决定

1. **音乐事实进 core**：新增 `packages/core/src/domain/content/`
   （`intervals.ts` / `chords.ts` / `scales.ts` / `degrees.ts` / `numerals.ts`），
   只存 **id 与半音结构**，外加语言无关的记号（`m2`、`maj7`、`Do`、`1`）。
   级数指向和弦 id（`quality: 'maj'`）而不是再抄一份半音排列，两处不会漂。
2. **纯算法进 core**：`domain/services/voicing.ts`（`voiceNumeral`）与
   `domain/services/melody.ts`（`planMelody` / `allowedMelodyPitches`）。
   后者接 `RandomSource` 端口，与出题器一致；core 里依旧没有 `Math.random`。
3. **显示名留平台**：`apps/web/src/i18n/domain-labels.ts` 只保留「id → 文案 key」的映射
   （音程/和弦/音阶的名字、参考曲目、播放方向符号）与音名/MIDI 换算。
   加一条内容因此要动两处：core 的内容表 + 平台的名字映射与两份字典。
4. **目录按职责重组**（web 侧）：`domain/` 拆成
   `course/`（课程表：模块、关卡、解锁）与 `questions/`（题型协议、生成器、播放事件、随机工具）；
   原先放在 `infrastructure/audio/events.ts` 的事件构造器移进 `questions/`——
   它是纯数据构造，不碰 Web Audio，放在基础设施层会造成「出题层反向依赖基础设施」。

## 后果

- 安卓端复用 range 扩大：不只是排序题，六个模块的乐理内容与两条生成算法都能原样拿走，
  平台侧只剩「怎么发声、怎么渲染、怎么存进度」。
- core 的测试从 51 个涨到 67 个：新增的 `tests/theory-content.test.ts` 守两类性质——
  表的结构（音程半音数唯一、和弦排列从 0 起严格递增、音阶公式以 12 收尾、音级恰好覆盖 0…11、
  级数引用的和弦真实存在、终止式落回主和弦）与算法的行为（200 条旋律全部落在允许音级内、
  跳进关真的跳出过五度、变化音只在邻音上且结尾不漂、查表遇到未知 id 一律抛错）。
- 代价是「加一条内容」变成两处改动，而且**只改一处不会被类型系统拦住**：
  `i18n.test.ts` 里那条「core 的每一条内容都有名字」的断言就是为此存在的
  （它比对 core 内容 id 与平台名字映射的 id 集合，多一个少一个都会红）。
- 代价之二是 core 从此会长「内容」而不只是「规则」。判据写在这里：**音乐事实进 core，
  产品与文案不进 core**。课程表、解锁、权重、连击、关卡完成口径仍然只在 `apps/web`（沿用 0003）。

## 考虑过的替代方案

- **维持现状，只补文档**：把「六个模块的乐理表与规则是 web-only」写进 0003 与 README。
  代价最低，但等于承认 core 的复用范围只有排序题；用户直接质疑了这一点，而且质疑是对的。
- **把整个课程（模块、关卡、解锁）也搬进 core**（0003 的选项 C）：core 会成为全课程唯一来源，
  但要重写一遍会话编排、与 `useSession` 重复，且「一关要连对几题」这类产品规则会污染领域测试。
  收益与其改动量不成比例。
- **只把表搬进 core，算法留在 web**：`voiceNumeral` 与旋律规则会被迫在平台侧重写一遍，
  而它们恰恰是最容易写错、最值得被测试覆盖的部分（现在有 5 条性质测试守着）。
