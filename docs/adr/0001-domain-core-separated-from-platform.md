# 0001 领域核心与平台实现分离（贫血模型的 DDD 分层）

日期：2026-09-27
状态：已采纳

## 背景

这个项目现在只做网页版，但已经确定以后要出安卓 app。产品形态本身很简单：弹几个音、拖几个滑块、判对错。
真正的问题不是「这一版怎么写最快」，而是**这一版的哪些决定会让安卓端和后续难度扩展返工**。

有三件事一旦写错，后面改起来很贵：

1. 出题与判分规则混进 React 组件或 Web Audio 调用里 —— 安卓端只能重写一遍规则，而且两份实现迟早会不一致。
2. 把「答案」存成用户猜的音高 —— 以后加音程判断、音级判断时，答案结构不够用，历史记录也要迁移。
3. 把播放时序、采样映射写死在播放器里 —— 换音色库或换平台时要重做，且无法测试。

## 决定

1. **`packages/core` 是平台无关的领域核心**，纯 TypeScript，不引用任何 DOM、Web Audio、React API。
   平台能力（播放音频、读写存储、随机数）一律通过 `domain/ports` 里的接口注入。
   判断标准是客观的：`packages/core` 里只要出现一个浏览器 API，这个边界就破了。

2. **采用贫血模型**：领域对象是纯数据类型（`interface`），没有任何方法；
   所有规则以纯函数形式放在 `domain/services`（出题器、判分器）与 `domain/entities`（如档位分配、排序名次）。
   这样规则集中在少数几个文件里，可被穷举测试，也不需要为了测试去构造复杂的对象图。

3. **应用层（`application/`）只做编排**：串起出题 → 播放 → 作答 → 判分 → 结算 → 存档，
   并把状态整理成界面可直接渲染的 view state。它不认识 React，界面通过订阅拿到状态。

4. **`apps/web` 只做适配与渲染**：Tone.js/Web Audio 播放器、localStorage 仓储、React 组件、依赖注入接线。
   界面不做任何业务推算（哪个档位被占用、能不能提交、还能听几次，全部来自 core）。

## 后果

- 安卓端可以原样复用 `packages/core`，只重写播放器适配器与界面。
- 难度扩展（音域、跨度、音数、将来的音程/绝对音高判分）大多只改 core，不动界面。
- 代价是多了一层 workspace 与若干端口接口；对这么一个体量的应用来说，这是刻意的投资，
  因为「以后要出安卓端」是已经决定的事，不是假设。

## 考虑过的替代方案

- **单包 + `src/domain/` 目录**：更简单，但「core 不许碰浏览器 API」只能靠自觉，安卓端复用时容易漏。
- **规则写在 React 组件里**：v1 最快，但安卓端必然出现第二份实现。
- **充血模型（领域对象自带方法）**：更符合经典 DDD，但与「贫血模型」的明确要求相悖，
  且对当前这点规则量来说，纯函数更容易测、更容易在界面里按需拼装。
